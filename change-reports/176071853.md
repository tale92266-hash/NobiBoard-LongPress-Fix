## Change 1 — Number row OFF by default: NO APK CHANGE WAS POSSIBLE (honest finding)

**The investigation proved the APK default is ALREADY false — in every place the value is defined.** There is no default left to flip; changing any of these would be a no-op. No file was changed for this request.

The number row (digit keys 1–0, layout `0x7f0e054b`, views E01–E10) renders only when the `enable_number_row` condition is true, gated in three places: QWERTY def `0x7f1707eb.xml` (`<if enable_number_row="true">` → include `0x7f17075f`), container `0x7f17000c.xml` (body `0x7f0e009d` with E-row vs `0x7f0e009c` without), theme `0x7f170002.xml` (layout theme `0x7f150390`). The condition reads SharedPreferences key `enable_number_row` (string `0x7f140944`).

**The default is false in all four authoritative sources (verified on the shipped 852 APK):**
1. **Preference-defaults array** `0x7f0300a2` (applied by `Lfav.a` → `Lqot.c` via `DefaultPreferenceValueParser.parseKeyValueEntryFromSystemProperties`): triple `[@string/0x7f140944 "enable_number_row", @string/0x7f1410c2 "ro.com.google.ime.number_row", @bool/0x7f050056]` — the default bool is **false** (confirmed by both apktool decode AND `aapt2 dump resources`: `resource 0x7f050056 bool … () false`).
2. **Restriction XML** `0x7f170001.xml`: `enable_number_row` `android:defaultValue="@bool/0x7f050056"` = **false**.
3. **Settings switch** `setting_preferences.xml` line 5 (`SwitchPreferenceCompat`, title "Number row", key `enable_number_row`): has **no `android:defaultValue`** → framework default **false**.
4. **Code fallbacks**: `Loye.c` reads it via `Lcei.x(0x7f140944, fallback=0)` = **false**; the pinyin path reads it with fallback 0 = **false**.
5. The bool `0x7f050056 = false` is the **stock Gboard 18.6.3 value** (present in the base XAPK's resources; no NobiBoard build ever changed it). Stock Gboard ships the number row OFF by default.

**What this means for Sam's phone — READ CAREFULLY:**
Because the APK default is already false, the number row showing on Sam's phone can only be a **persisted `true`** in his NobiBoard SharedPreferences (written when the switch was toggled ON at some point — the switch sits at the top of Settings → Preferences), or the system property `ro.com.google.ime.number_row` set on his Vivo (unlikely; not checkable from here). **An APK-default change cannot turn off a persisted `true`.** This build therefore does NOT change the number row on his current install.

**The fix for his phone is one manual toggle:** Settings → Preferences → **"Number row" OFF**. After that, the row stays off (and the setting remains available to turn back ON). The alternative — a one-time pref reset inside the app on upgrade — was **NOT** done: the brief forbids silently resetting Sam's saved preferences, and it needs his explicit approval. (Same class of evidence as the old `show_secondary_digits` anomaly: defaults don't move an already-seeded pref.)

**Corroborating layout facts (found during the investigation):** D01–D10 = the top LETTER row (Q–P; confirmed by the Phase 2 report), E01–E10 = the digit row, G01–G10 = the emoji row (40dp, `0x7f0e0099`, included in both bodies). The emoji row is NOT gated on `enable_number_row` — turning the number row off cannot hide the emoji row.

## Change 2 — Keyboard height BIGGER by ~one row: ratio default 1.0 → 1.2

**Mechanism (found, not invented):** keyboard height = base height × ratio. The ratio is a set of `Lodi` flags in `Lpfd` (`KeyboardHeightRatio`, classes.dex): base flag `config_keyboard_height_ratio` (default "1.0", overridable by system property `ro.com.google.ime.height_ratio`) plus six variants (portrait / landscape / normal_portrait / normal_landscape / foldable_portrait / foldable_landscape), all default "1.0". All seven flags share **one** default string, loaded once by `Lpfd.<clinit>` insn 6 (`CONST_STRING v2, "1.0"`). There is **no in-app keyboard-height slider** in this build (the slider in `setting_preferences.xml` is `keyboard_slide_sensitivity_ratio`, not height), so the flag default IS the effective default. The flags are not persisted anywhere (no Settings UI, not in the `Lfav.a` defaults arrays) — so the new code default takes effect on Sam's existing install the moment the new build runs.

**Exact change (dex, ONE instruction):**
- `Lpfd.<clinit>` insn 6: `CONST_STRING v2, "1.0"` → `CONST_STRING v2, "1.2"` (new string-pool entry; the shared `"1.0"` pool entry was the only CONST_STRING "1.0" in the whole classes.dex — verified by scan — and is now unreferenced). Same opcode (21c), same register, same 2-code-unit size: code size, offsets, branches, registers unchanged. Dump diff orig→patched `Lpfd.<clinit>`: exactly 1 line.
- **Before/after:** ratio default `1.0` → `1.2` = **+20% total keyboard height**. The keyboard has ~5 rows (emoji 40dp fixed + 3 letter rows + space row); a letter row is ~52–60dp on a ~250–290dp portrait keyboard, so +20% ≈ **+50–58dp ≈ one key row**. The emoji row stays 40dp (fixed height in `0x7f0e0099`); the extra height goes to the letter/space rows via their weights (weightSum 1000, letter-row weight 333 in the number-row-OFF theme `0x7f15038a`). Key widths, popup size/shape, emoji row, and long-press behaviour untouched.

**Exact change (resource, for consistency):**
- `res/xml/APKTOOL_DUMMYVAL_0x7f170001.xml`: all six `config_keyboard_height_ratio_*` restriction entries `android:defaultValue="1.0"` → `"1.2"` (exactly 6 replacements, and no `defaultValue="1.0"` remains in that file). This keeps the managed-config default consistent with the flag default, whichever source the flags system consults first.

**Why not the theme/mm-preset route:** the height presets (33–52mm, styles `0x7f150381–388`) set per-form-factor base dimensions, but the active preset is chosen by device-form-factor code and the values are already scaled by the ratio — the ratio is the designed height scaler, so changing it is the minimal, uniform lever. Row weights (`0x7f040209`/`0x7f040287`, weightSum 1000) only redistribute height among rows; they cannot make the whole keyboard taller.

## Build notes (record, do not repeat)
1. `RatioPatch` first failed its own assertion (`Lpfd.<clinit>` has **35** insns, not 34 — the earlier DumpMethod read was miscounted by one; RETURN_VOID is insn 34). The assertion caught it before any write; fixed to 35.
2. `page_align.py` takes TWO positional args (`page_align.py <in> <out>`) — `align_apk` is the function name inside the script, NOT a CLI subcommand. Calling it with `align_apk` as argv[1] fails with FileNotFoundError.
3. `strings` on a dex does not reliably extract short pool strings — use StringSearch/DumpMethod for pool-string checks, not `strings -x`.

## What could NOT be verified on-device (Sam's phone test is the only verdict)
1. **Height increase is UNPROVEN live.** What IS proven: the ratio default that the height flags read is now 1.2 in both the dex flag default and the restriction default, the patch is exactly one instruction, and every gate passes with the Phase 3 Fix profile. What is NOT proven: that the height computation on Sam's Vivo actually multiplies by this flag (the flag consumer reads via the `Lwpm` registry by name, which static analysis could not trace end-to-end), that the visible keyboard is ~one row taller, and that the popup still positions correctly on the taller keyboard. If the keyboard does NOT get taller, the next step is a height-diagnosis (check which ratio source wins: flag default vs restrictions bundle vs phenotype), not another blind patch.
2. **Number row: this build does NOT turn it off on Sam's phone** (see Change 1). He must toggle it off once in Settings → Preferences → "Number row". If it is STILL on after that toggle, the cause is the `ro.com.google.ime.number_row` system property or a stale IME def cache — report it, do not rebuild blind.
3. The popup fix, editor, and custom-emoji substitution are unchanged (classes2/classes6 byte-identical) but their live behaviour is re-proven only by Sam's test, as before.
4. Install-over behaviour from Phase 3 Fix (same key, versionCode rise) follows the fixed-key pattern used by every previous build, but was not installed here.
