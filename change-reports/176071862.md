## Why this build exists (diagnosis-861)

Sam's 861 report: the keyboard does not open AT ALL after installing 861
("FR wahi dikkt keyboard hi na open hona"). Diagnosis-861
(`~/workspace/apk-edits/nobiboard-2026-11-11-longpress-defparse-diag4/outputs/diagnosis-861.md`)
proved the ROOT CAUSE:

**The P0 Toast in `Lpud.m` throws on the def-parse thread and kills the
keyboard-definition load.** 861 is the first build in which the `Lpud.m`
diagnostic Toasts actually FIRE (in 858/859/860 they were always skipped
because the Context was null on the first def-parse call). The P0 Toast
(`"DEF 859: Lpud.m runs"`, insns 44–48) fires on the FIRST `Lpud.m` call of
the process. `Toast.makeText()` on a thread with no `Looper` throws
`NullPointerException: "Can't toast on a thread that has not called
Looper.prepare()"` (proven from AOSP `Toast.java`). `Lpud.m` has **0 tries**,
so the throw propagates (`Lpud.m` → `Lpwz.f` 0 tries → `Levj.a` 0 tries →
`Lcwj.call` rethrows) and the module-load `FutureTask` completes
exceptionally. `ModuleInfo.loadModule()` catches the `ExecutionException`,
logs `"Failed to get module from moduleFuture"`, and **returns null** — no
keyboard definition → **keyboard cannot open**. The `FutureTask` is created
once and cached, so the failed Future is reused on every later attempt: the
keyboard never opens again for the whole process. No crash dialog, no visible
log — exactly Sam's symptom (keyboard never opens, Settings/editor still work).

Ruled out (do NOT chase): `Lmxa.attachBaseContext` throw (SAFE — original 4
insns: super `attachBaseContext` + `Lvqt.b(Context,Z)`; NO `MultiDex.install`;
Application-only); `Lpud.<clinit>` throw (HARMLESS — 5 insns, `Lpux` trivial,
all referenced classes in classes.dex primary); substitution throwing for
Sam's exact value `😂,🥰,💕,💖,😘` (throw-free — split = exactly 5 parts, all
non-empty; slots in-bounds; `arraycopy` length-mismatch REFUTED;
`[I` null REFUTED); Block L' / Block E throwing; stale install; any
popup-path involvement (classes2 byte-identical to Fix11).

## Change 1 (MUST-HAVE) — Remove ALL FOUR Toast call sites from `Lpud.m`

Sites (verified by `ReferenceInstruction`, never `toString()`):
- P0 insns 46/47/48 — msg `"DEF 859: Lpud.m runs"` (idx 44)
- P1 insns 227/228/229 — msg `"A: prefs="` (idx 219)
- P2 insns 337/338/339 — msg `"A: SUB OK"` (idx 335)
- P3 insns 453/454/455 — msg `"A: GUARD"` (idx 446)

Each site = `INVOKE_STATIC Toast.makeText` (35c, 3 units) +
`MOVE_RESULT_OBJECT v6` (11x, 1 unit) + `INVOKE_VIRTUAL Toast.show` (35c,
3 units). Replaced with **SEVEN NOPs (3+1+3)** so the total code-unit count
is IDENTICAL (917 units, unchanged) and every instruction boundary stays at
the same address — therefore EVERY branch offset in the method is unchanged
and NO retargeting was needed (verified programmatically: every original
branch offset + target identical after the change). The `CONST_STRING` message
loads stay (dead, harmless). New `Lpud.m`: 510 insns before the handler.

**KEPT:** the `Log.e` calls (4, never throw) and the `nobi_diag`
SharedPreferences writes (Block L' `last_run` + Block W `last_a` — safe, and
they are the reliable on-device diagnostic). The Diagnostics section in the
editor is how Sam verifies the fix.

**method_ids note:** NOP-ing the 4 Toast call sites removes the LAST
references to `Toast.makeText` + `Toast.show` in classes.dex, so the
DexBuilder drops exactly those 2 unreferenced refs: method_ids 57,519 →
57,517. Proven with `MethodRefScan` on the patched dex: DROPPED = exactly
`Toast.makeText` + `Toast.show`, ADDED = nothing. field_ids UNCHANGED
(38,010). No referenced method was removed.

## Change 2 (SHOULD-HAVE) — ADDED: catch-all try block around the hook region → GUARD

**The try/catch WAS added and all gates pass with it** (no fallback needed).

- Try region: old insns [49..382) — the P0-Log fingerprint through the
  substitution + clean-up. In the new layout: new idx [53..394), code-unit
  addresses [92..710), count 618. `TryCheck` on the patched dex:
  `m regs=16 insns=513 tries=1, try start=92 count=618 handlers=1`
  (catch-all — exception type null).
- Handler (appended at the end of the method, after the final `goto/16`):
  - `510: MOVE_EXCEPTION v0`
  - `511: CONST_4 v0, 0` (discards the exception object so v0 is INT at the
    GUARD join — INT on the normal path too, so the merge is INT-vs-INT)
  - `512: GOTO_16 -> GUARD` (new idx 456 = old 444, addr 819, off −100;
    verified by BranchDump: `512 addr=397 GOTO_16 -> idx 456 (addr 333)`)
- New `Lpud.m` total: **513 insns, 921 units** (delta +4, even — payload
  alignment parity preserved; the method has 0 payloads).
- Why the GUARD merge is clean: v0 is an INT scratch throughout the hook
  (the wide J in Block L' is reset to INT(0) at insn 27, before the try
  region starts at 49); the handler sets v0 = INT(0) before the GOTO, so at
  the GUARD join v0 is INT on both paths. TypeMergeCheck confirms: **1 = 1
  stock, no new conflict** (see gates).

This is the hardening that makes the fix PERMANENT: any future hook throw
(a prefs edge case, a malformed saved value, a new Android behaviour) now
falls through to GUARD/defaults instead of propagating out of `Lpud.m` and
killing the def load. The keyboard can never be killed by the hook again.
