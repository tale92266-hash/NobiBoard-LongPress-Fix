## Bugs found and fixed in DiagPatch.java (previous agent's draft)

The previous agent's `DiagPatch.java` had three real bugs, all found and fixed while finishing the build (the draft would not compile / would have produced a broken method):

1. **`NEW_INSTANCE` is format 21c, not 22c.** The draft used `ImmutableInstruction22c(Opcode.NEW_INSTANCE, ...)` (3 args) — dexlib2 rejects it at runtime (`IllegalArgumentException: Invalid opcode new-instance for Format22c`). `NEW_INSTANCE` takes one register + a type reference = format 21c. Fixed in `emitSbMsgInt` / `emitSbMsgStr`.
2. **P3 placement was inconsistent (Layout A vs Layout B).** The draft's assembly placed P3 *before* orig 245, but its base computation (`base3 = origTotal + s0 + s1 + s2`) and its header comment ("P3 appended at the end of the method, after RETURN_VOID") assumed Layout B. The sanity check would have aborted, and — worse — P3 in the fall-through path would have fired `"A: GUARD"` on the SUCCESS path too. Fixed to Layout B: P3 appended after orig 311 (RETURN_VOID), reachable ONLY via the retargeted GUARD branches; the SUCCESS fall-through (P2 → clean-up) never reaches it. Verified: P3 starts at addr 681 = base3; its GOTO_16 (addr 709 → clean-up 567, off -142) lands on the clean-up.
3. **`emitLog` clobbered the message in P1.** It loaded the tag into R_PARTS (v8) and then called `Log.e(v8, msgReg)` — but in P1 the message itself is in v8, so the tag load overwrote it and the Log would have shown `"NobiDiag"` as both tag and message (the prefs value lost in logcat). The Toast was unaffected (it uses v8 before the Log). Fixed: `emitLog` now takes a separate `tagReg`; P1 logs with tag in v11 (free after the message is built) and message in v8. Verified in the dump: P1 insn 192–193 = `CONST_STRING v11, "NobiDiag"` + `Log.e(v11, v8)`.

**Branch-region verification (independent of the patcher's vacuous check):** the patcher's "all non-GUARD branch offsets unchanged" loop compares each copied instruction's offset to itself, so it proves nothing. I verified the region claim by hand from a full `BranchDump` of the 858 `Lpud.m`: all 11 GUARD branches target orig 245 ([2, 131, 136, 141, 145, 151, 156, 161, 166, 171, 176]); every non-GUARD branch has source and target in the same region ([0,146) / [146,245) / [245,312)), so the insertions at 146 and 245 shift both ends equally and the offsets stay correct.

**Register discipline (hand-verified on the dump):** instrumentation uses only the hook's own scratch (v0, v1, v2, v5, v6, v7, v8, v11), each holding ONE kind. Every `MOVE_RESULT` destination is a proven-dead scratch (v1/v5/v6/v7/v8); colId (v4) is never a `MOVE_RESULT` destination (the v13-lesson from diagnosis-857, applied here as v4). v2 is INT throughout. The clean-up (orig 245) resets v3/v6/v7/v8/v11 to INT(0) before the original code, which uses them as INT — the instrumentation leaves them in the same kinds the hook does, so the clean-up is unaffected.
