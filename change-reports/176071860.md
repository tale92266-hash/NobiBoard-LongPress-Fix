## Why this build exists
Sam confirmed he did everything on 859 (force-stop after installing, verified the
version, latest) — still no Toast, still defaults. Stale-install is RULED OUT.
Diagnosis-859's leading cause: `ActivityThread.currentApplication()` is NULL at
def-parse time (def-parse runs on a background executor during early startup),
so the 858 hook goes to GUARD and the Toast is skipped. This build fixes the
Context source AND replaces the unreliable transient Toast with a persistent
diagnostic Sam can read in the editor.

## Change 1 — Fix the Context source (the actual fix)
**Hook point: `Lesb.onCreate()`** — the Application base class's `onCreate`.
- Neither `HiltLatinApp` nor `LatinIME` declares `onCreate()` (both contain only
  `<init>`). `HiltLatinApp` extends `Lesb` (which HAS `onCreate()V`, 9 insns,
  2 regs, 0 tries). `Lesb` → `Lesf` → `Lmxa` → `Lpdy` → `android.app.Application`
  → `Context`, so `this` (v1, type `Lesb`) IS assignable to `Context`.
- `Lesb.onCreate` runs on the main thread, `this` IS the Application Context,
  and it runs before any Service/Activity is created — hence before any
  def-parse. Verified: `IF_NEZ` at idx 1 targets idx 7 (`INVOKE_SUPER`); the
  one-shot guard (`Lesb->g:Z`) is preserved.
- **The hook:** ONE instruction inserted at idx 0:
  `SPUT_OBJECT v1, Lpud->appCtx:Landroid/content/Context;` (2 units, even;
  insert-at-0 preserves the `IF_NEZ` offset — verified still +11, targets
  final idx 8). The field is **public static** (flags 0x9) because it is
  accessed cross-class. Tiny, null-safe, no behaviour change to the method.

**New static fields on `Lpud` (3, classes.dex field_ids 38,007 → 38,010):**
- `appCtx:Landroid/content/Context;` (public static, 0x9)
- `diagCtxSrc:Ljava/lang/String;` (private static, 0xA)
- `diagPrefs:Ljava/lang/String;` (private static, 0xA)
- No new METHOD refs (method_ids stays 57,519) — `currentTimeMillis`,
  `append(J)`, `getSharedPreferences`, `edit/putString/apply`, Toast, Log.e,
  StringBuilder are all already in the 859 pool.

**`Lpud.m` hook (859: 387 insns → 860: 498 insns, 16 regs, ONE dexlib2 pass):**
- **Block E (entry, 14 insns, 24 units):** reset `diagPrefs` to null;
  `SGET_OBJECT v5, appCtx` → if non-null use it (`"static"`), else fall back
  to `currentApplication()` (`"fallback"`), else `"null"`; store the source
  string into `diagCtxSrc`. After E, v5 = resolved Context (or null).
- **NOP replacements (same units, no shift, no retarget):** the three OLD
  `currentApplication()` fetches are NOP'd out so they cannot overwrite v5
  with a null — P0 fetch (orig idx 5–6), prefs fetch (orig idx 165–166),
  P3 fetch (orig idx 375–376). Each `INVOKE_STATIC` (3 units) → 3 NOPs;
  each `MOVE_RESULT_OBJECT` (1 unit) → 1 NOP. Verified: exactly 4 NOPs at
  each site (final idx 43–46, 205–208, 451–454); only ONE `currentApplication`
  invoke remains in the method (Block E's fallback, final idx 4).
- **The rest of the `Lpud.m` hook logic is IDENTICAL to 858** (fingerprint,
  26-way chain, split=5 parts + every part non-empty, clone + 5
  substitutions, GUARD, v13-colId-clobber fix). Only the Context source
  changed.
- **Branch retargeting (16, computed from final addresses, verified):**
  idx 2 (`IF_NEZ` → P0_SKIP 30), idx 178 (`IF_NE` → P1_SKIP 195),
  idx 295 (`IF_NE` → P2_SKIP 304), idx 373 (`IF_NE` → P3_SKIP **385**, the
  NOP — NOT 386; the summary's "386" was wrong, BranchDump proved 385),
  idx 386 (`GOTO_16` → clean-up 305, offset decreases), and the 11 GUARD
  branches → P3 (372). All other original branch offsets verified
  UNCHANGED. The 25 chain `GOTO_16`s still target idx 165 (now a NOP — same
  address, so no retarget needed).
- **MOVE_RESULT audit (v13-colId lesson):** my blocks' `MOVE_RESULT`
  destinations are only v6 (REF scratch), v8 (REF scratch), v0 (wide in
  Block L, reset to INT(0) after use), v5 (ctx in Block E's fallback,
  intended). NO `MOVE_RESULT` into v4 (colId), v13, or v15 from my blocks.
  The two such instructions in the final method (final idx 406 `MOVE_RESULT
  v4`, idx 443 `MOVE_RESULT_OBJECT v13`) are the ORIGINAL code's own
  instructions (identical at 859 idx 330/367) — untouched.

## Change 2 — Reliable diagnostic (SharedPreferences + editor section)
**NOT a Toast** (859's Toasts were never seen by Sam). The hook writes a
persistent record to SharedPreferences file **`nobi_diag`**, and the editor
activity displays it in a new **"Diagnostics"** section at the bottom of the
editor UI.
- **Block L (24 insns, 48 units, inside P0's first-call branch):** on every
  def-parse, writes `last_run = "run ts=<currentTimeMillis>"`. The wide J
  (v0/v1) is reset to INT(0) after `append(J)` so it cannot leak into P0's
  type merge.
- **Block S (1 insn, 2 units, end of P1, A-key only):** stashes
  `diagPrefs = v7` (the prefs string actually read for key A).
- **Block W_SUB (33 insns, 68 units, after P2, A-key only):** on the SUB
  path writes
  `last_a = "A cp=1f496 ctx=<diagCtxSrc> prefs=<diagPrefs> outcome=SUB OK"`.
- **Block W_GUARD (33 insns, 68 units, after P3's Log, A-key only):** on the
  GUARD path writes the same record with `outcome=GUARD`. Appending a null
  String appends the literal `"null"`, so an early GUARD (before the prefs
  read) reads `prefs=null` and a late GUARD / SUB reads the actual prefs
  value — the record distinguishes early vs late GUARD without a reason code.
  (The specific GUARD reason — size≠9, chain no-match, prefs null, parts≠5,
  empty part — is NOT recorded as a separate field; the combination of
  `ctx=` + `prefs=` + `outcome=` narrows it to the same conclusion. If the
  record shows `ctx=static` + `prefs=<value>` + `outcome=GUARD`, the failure
  is in the split/parts/chain checks, not the Context.)
- **Editor (classes6.dex):** new "Diagnostics" section (header + hint +
  record TextView) at the bottom of the editor, after the bottom bar.
  `refreshDiag()` reads `nobi_diag` (`last_run` + `last_a`) fresh and shows
  them; called at the end of `onCreate` and in a new `onResume()` override
  (so it refreshes when Sam returns to the editor after using the keyboard).
  Shows "No diagnostic record yet — force-stop the keyboard once and open
  it, then come back here." if nothing was recorded. App UI text is English.
- **Why SharedPreferences, not a file:** the record is written from `Lpud.m`
  where a Context is available (once Change 1 fixes it); the editor (same
  package, same process) reads the same file — `getSharedPreferences`
  returns the same cached instance, so `apply()` updates are visible.
  A file fallback was rejected: raw FileOutputStream to /sdcard/Download
  fails under scoped storage on Android 16, and the V44/V47 DiagLogger's
  MediaStore write FAILED on Sam's phone. If the Context is STILL null
  (Change 1 failed), no record can be written at all — the editor shows
  "no record" and the popup shows defaults, which together indicate the
  Context is still null.
- **The 859 Toasts are kept as-is** (P0/P1/P2/P3) for continuity; the
  reliable record is the SharedPreferences one.

## Editor rebuild note (important)
The editor was recompiled with **JDK 17 default** (class file version 61,
nest-based `-$$Nest$` synthetic accessors) — the SAME as the Phase 3 build.
My first attempt used `-source 8 -target 8` (Java 8, legacy `access$`
accessors), which produced a CanonDiff of 55 methods against 859. Rebuilding
with JDK 17 default brought it to 6. **Lesson: match the original
compilation target when rebuilding a dex; a different target regenerates
all synthetic accessors.**
- The remaining 3 `<clinit>` diffs (Defaults, EmojiData,
  NobiEmojiEditorActivity) are a **d8 instruction-selection artifact**, NOT
  a logic change: d8 in this run emitted `FILLED_NEW_ARRAY` (compact) where
  the Phase 3 run emitted `NEW_ARRAY` + `APUT_OBJECT` (verbose) for the
  same array initializers. Sources Defaults.java / EmojiData.java are
  byte-identical to Phase 3; the javac .class bytecode is identical
  (verified). The data initialized is identical; only the instruction
  encoding differs. `FILLED_NEW_ARRAY` is a valid standard dex instruction.
  Rebuilding with/without `--lib` and with `--debug` did not change this
  (the Phase 3 d8 run must have used a different d8 build); it is not
  worth chasing — the code is correct and more compact.
- The `-IA` synthetic class: present in the Java 17 build (14 classes,
  matching Phase 3); dropped in the Java 8 build (13 classes) because d8
  did not generate it. It is an empty synthetic d8 artifact, referenced
  only by its own descriptor + a synthetic constructor — dead code. The
  Java 17 build keeps it, so classes6 has no removed class.

## Honest caveats
- The live runtime behaviour (whether appCtx is actually set before def-parse,
  and whether the custom emoji appears) is UNPROVEN on-device — Sam's phone
  test is the only verdict. This build is designed to MAKE the outcome
  observable (the Diagnostics section), not to assume it.
- The `last_a` record does NOT include the specific GUARD reason code (which
  check failed). The `ctx=` + `prefs=` + `outcome=` combination narrows it,
  but if the record shows an unexpected GUARD, the next diag would need the
  reason. (Not built — do not build a second variant unless Sam's report
  requires it.)
- The Diagnostics section only records key A (the key Sam tested with HAHA).
  Other keys' outcomes are not recorded. `last_run` records every def-parse.
- The editor's `<clinit>` methods differ from 859 only by d8's
  FILLED_NEW_ARRAY instruction selection (same data, same logic) — see above.
