## The def-parse method found (how it was located)
- The string `"long_press_data"` appears in **NO dex** — softkey attributes are reached via a `SPARSE_SWITCH` on the attribute name's hashCode in `Lpwt.e(AttributeSet;I)V` (which handles `long_press_delay`, `popup_timing`, … but NOT `long_press_data`).
- `Lpxa.a(Ltjb;)V` (267 insns) is the keyboard-def XML node parser (`softkey_list` at insn 121, `softkey` at 140). `Lpwz.f()` (276 insns) is the softkey **template expansion**: it copies template values into the `Lpwt` builder, then iterates its `Lpue` action entries and for each calls **`Lpud.m([I,[Lpuz;,[Object;)V` (insn 110)** — which builds the `Lpva` list from the parsed code-point / Lpuz / label arrays — then `Lpud.c()` (insn 198) and `Lpwt.o(ActionDef)` (insn 201). Finally `Lpwt.b()` builds the SoftKeyDef. So **`Lpwz.f` → `Lpud.m` IS the fd2 def-parse path for the letter-key long-press lists.**
- **`Lpud.m([I,[Lpuz;,[Object;)V` (62 insns, 16 regs, 0 tries, 0 payloads) — CHOSEN HOOK POINT.** It converts the parsed arrays into the `Lpva` list: empty/null arrays → stores the empty list `Lwmm.a` into `Lpud.b`; otherwise it loops over the code points, creating each `Lpva` with `g = 0x7fffffff`, adding to a `Lwgz` builder, then stores the built `Lwhe` into `Lpud.b`. Params: v12 = this (`Lpud`), v13 = `[I`, v14 = `[Lpuz;`, v15 = `[Object;`. Locals v0–v11 are DEAD at method entry (written before read on every path), so the hook uses them as scratch **without growing the register count and without remapping**.
- Rejected alternatives: `Lpud.n([Lpva;)V` (general funnel called from many contexts — `Lpgs.<init>`, `Lmmh.e`, `Lpud.s`, `Luya.aM`, classes2 accept methods — NOT specifically the fd2 path, and only ~3 registers); `Lpud.c()` (only validates + calls the ActionDef constructor); `Lpgs.<init>` (builds "default"/"recent_softkeys_" ActionDefs from `Lpfs.a(String)` lists, NOT the fd2 letter-key lists).

## Why this point is safe (and NOT a long-press code)
- `Lpud.m` runs at **keyboard-def load**, not at popup time. No popup class/method is in its call chain.
- Inserting at **insn 0** shifts EVERY original insn by the same +grow, so **every original branch offset is UNCHANGED** (verified: the original 62-insn block is textually identical after the patch, and the patcher asserts this). No original branch retargeting was needed.
- The hook only **substitutes the two input arrays** (v13/v15) before the original code runs; on any failure it leaves them untouched and the original code runs exactly as stock.
- **CanonDiff vs 856: classes.dex = exactly 1 CHANGED method (`Lpud.m`); classes2 = 0; classes3 = 0; classes4 = 0; classes6 = 0 (editor); classes5 = 1 (version string only).** `Lqmu.c()` and `Lqml.c()` are **byte-identical to 856/Fix11** (classes2.dex md5 `87aeab3d847cba2edcc55e4c4f12e5e0` both).

## Hook design (250 insns, 454 code units — even)
Patcher: `tools/src/DefParsePatch.java` (+ `Phase3Tables.java`, the `B` label-based builder). ONE dexlib2 pass on classes.dex only; classes5 bumped once by a separate `VerBump858` (856 → 858, 3 replacements).
1. **Fingerprint** — `[I` length must be 9; `AGET v13,3` → centre code point into v2. (Size-9 + item[3] is the 9-token fd2 list; the centre token is unique across all 26 keys.)
2. **26-way chain** — on the centre code point → pref key `emoji_A`…`emoji_Z` + column class (0 = centre, 1 = left edge q/a/z, 2 = right edge p/l/m). Uses the same `LOOKUP_CP[26]` / `LOOKUP_COL[26]` tables as Phase 3 (`tools/src/Phase3Tables.java`). Any miss → GUARD.
3. **Prefs read** — `ActivityThread.currentApplication()` (the ONE new method ref in classes.dex, which has 8,020 free method_ids; 57,516 → 57,517) → `getSharedPreferences("nobi_longpress_emoji", 0)` → `getString(key, null)`. Any null → GUARD. Context for prefs comes from the application, so it is available at def-parse time.
4. **Empty-part guard (diagnosis-857 Candidate 1)** — `split(",")` must give exactly **5 parts AND every part's `length() > 0`**, else GUARD. (`codePointAt` on `""` throws `StringIndexOutOfBoundsException`.) Parts are in canonical order `center,up,down,left,right`.
5. **Clone** — `NEW_ARRAY` + `System.arraycopy` for both arrays (9 elements each). (`Arrays.copyOf` refs do not exist in classes.dex, so cloning uses `NEW_ARRAY` + `System.arraycopy`, both already present.) The ORIGINAL arrays are never mutated.
6. **5 substitutions** — for each part, `codePointAt(part, 0)` → `APUT` into the cloned `[I` at the computed slot, and the part string → `APUT_OBJECT` into the cloned `[Object;` at the same slot. Slot indices computed **on the fly from the column id** (the 857 pattern): centre `{down 0, centre 3, right 4, left 5, up 6}`; left `{1,4,5,3,7}`; right `{1,4,3,5,7}`. Part→slot: centre part0, up part1, down part2, left part3, right part4.
7. **Finalize** — `MOVE_OBJECT v13, cloneI; MOVE_OBJECT v15, cloneO`; falls through to the original insn 0 (which then builds the `Lpva` list from the **custom** arrays, with `g = 0x7fffffff` exactly as stock does).
8. **Clean-up (GUARD target)** — resets v3, v6, v7, v8, v11 to `CONST_4 0` before the original code runs. **Why:** the hook leaves REF values in those registers (pref key, prefs, prefs string, parts array, part string), but the original code uses them as INT locals; on the empty-arrays path they are never rewritten by the original code, so their REF types would flow to the loop head / RETURN and merge INT-vs-REF. Resetting them to INT makes every merge INT-vs-INT. v5/v9/v10 are **NOT** reset — they are REF in the original code too (`Lwgz` / `Lpuz` / `Lpva`), so resetting them to INT would CREATE a conflict. v13/v15 (the arrays) are deliberately untouched by the clean-up.

**v13 colId clobber fix (diagnosis-857):** every `MOVE_RESULT` / `MOVE_RESULT_OBJECT` destination is a proven-dead scratch — ctx→v5, prefs→v6, prefs-string→v7, split→v8, `length()`→v1, `codePointAt`→v1. The column id (v4) is **never** a `MOVE_RESULT` destination. Register discipline: v0 = INT temp (slot/const), v1 = INT temp (length/code point), v2 = INT centre CP, v3 = REF pref key, v4 = INT colId, v5 = REF Context, v6 = REF SharedPreferences, v7 = REF prefs string, v8 = REF parts array, v9 = REF cloned `[I`, v10 = REF cloned `[Object;`, v11 = REF part string. **Each scratch holds exactly ONE kind** (INT or REF) across the whole hook — the two string constants (prefs name, `","`) live in v11 (REF-kind), NOT v0 (INT-kind), so no kind ever flips at a GUARD merge. v12 (`this`) and v14 (`[Lpuz;`) are NEVER written.

**No label update.** The ActionDef list is substituted before any popup is built, so the popup's cells/labels are correct from the start.

## Honest caveat — the reload question (tell Sam)
The def-parse hook runs at **keyboard-def load time**. The keyboard def is parsed when the keyboard is created and may be **CACHED** (Gboard reloads defs via `Levj.a()`'s reload list for its own preference keys; the custom `nobi_longpress_emoji` SharedPreferences file is separate, so it does not trigger a reload automatically). **So after Sam customizes an emoji, the change may only appear after the def is re-parsed (force-stop / keyboard restart).** This was NOT solved in this build — it is the price of not touching the long-press codes. **Tell Sam: after customizing, force-stop once for the change to take effect** (to be confirmed by his test). If the change does NOT appear even after a force-stop, that is new device evidence — do not rebuild blind.
