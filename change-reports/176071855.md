### The accessors — `SilkRectangularPopupView.o()` / `p()` (classes2.dex, smali in source-share)

- **`o(Ltqb;)Landroid/animation/Animator;`** (smali line 1386): reads `j[1]`. Null-checks: content view `f` non-null, array `j` non-null, element `j[1]` non-null — any null → returns null (`:cond_14`). Otherwise `setTarget(view)` + `Ltqb.i(animator, this, 1)`.
- **`p(Ltqb;Z)Landroid/animation/Animator;`** (smali line 1842): reads `j[0]`. Null-checks: LinearLayout `e` non-null, view `f` non-null, array `j` non-null, element `j[0]` non-null — any null → returns null (`:cond_68`). Otherwise (if AnimatorSet) rescales the child ObjectAnimators by the popup's measured width, `setTarget(view)` + `Ltqb.i(animator, this, 0)`.

**Yes — there ARE null checks.** Both accessors null-guard the array and the element and return null. `Ltqb.A` null-guards res id 0. Nothing crashes at load or at accessor level when `show_animation` is absent.

### Where the null goes — the two callers (found via FindCallers on the `Ltdt` interface; the concrete class is never invoked directly)

- **`Lqck.D` (classes2.dex, the long-press popup-show handler)** calls `Ltdt->p` (insn 268) and stores the result in the popup show-request's animator field: `IPUT_OBJECT v9, Lqog->c:Landroid/animation/Animator;` (insn 282). The request is then shown via `Lqnh->v(Lqok;)` (insn 288). **In 854, `p()` reads array[0] = the null show slot, so `Lqog.c` is null — the popup show-request carries a NULL animator.** In 853/855 (show_animation present) `p()` returns the real show animator and `Lqog.c` is non-null.
- **`Lqmi.a` (classes.dex, popup controller)** calls `Ltdt->o` (reads array[1] = the hide animator, non-null even in 854) and passes it to `Lqnh->l(View, Animator, Z)` — the framework show/hide call.

### Is there an explicit re-show / dismiss path when the show animator is missing?

**NOT found in the available smali.** No code path in the APK explicitly re-shows or dismisses the popup when the show animator is null. The classes that consume the show-request animator (`Lqnh` — an interface, access 0x601, with NO implementation in any of the 6 app dexes; `Lqog`, `Lqok`, `Ltdr`) live outside the APK (framework / runtime), so the exact come-and-go loop inside them cannot be read from here.

**What IS proven:** removing `show_animation` did not just remove a fade-in — it put a **null animator into the popup show-request** (`Lqog.c`), which is the ONLY popup-show difference between 853 and 854. The show-request animator is what the framework uses to run/complete the popup show; a null there is a concrete, mechanism-level reason the show can misbehave (appear-then-dismiss / re-trigger) while the press is held. Restoring `show_animation` (this build) restores a non-null show animator in the array, so `p()` returns it and `Lqog.c` is non-null again — exactly the Fix11 state.
