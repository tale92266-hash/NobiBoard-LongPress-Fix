## 1. Analysis — WHY the Phase 3 hook broke the popup

**The hook is PROVEN the cause — by removal.** The hook code was byte-identical
(classes2 md5 `d641d51e…`) across 852/853/854/855 while the symptom kept getting worse,
and removing it (856, `Lqmu.c()` = Fix11's exact 101-insn version, classes2 byte-identical
to Fix11) fixed the popup on Sam's phone. The show_animation was refuted as the cause
(855 restored it and the popup still failed). So the hook — and nothing else — broke it.

**The exact micro-mechanism is NOT proven statically** (no device log, no runtime trace).
What the evidence rules in and out:

| Candidate | Verdict | Evidence |
|---|---|---|
| `Lqmu.c()` hook SIZE (321-insn / 584-unit insertion) | Possible contributor | The insertion more than quadrupled `c()` (101 → 436 insns) and changed its structure. But `c()` is a build-time method, not a per-frame path, so size alone is a weak explanation. |
| SharedPreferences read latency in the popup-build path | Ruled OUT as the sole cause | In 852/853 the flicker persisted on UNcustomized keys — after the first call, `getSharedPreferences` + `getString` are framework-cached in-memory lookups (microseconds), too small to explain persistent flicker. A first-call disk read could explain a single first-open stutter, not repeated flicker. |
| Substitute-after-registry-build + label repair | **Strongest candidate** | The Phase 3 hook substituted the list into `Lqml->e` AFTER `Lqmu.c()` had already built the popup views/registry from the ORIGINAL list, then tried to repair the mismatch by walking the tracker registry (`Lqmr.d`) and calling `TextView.setText` on cells during the build. The hook ran inside the time-critical popup-build path and mutated view state the builder had already bound. The worsening 852 → 854 → 855 while the hook stayed byte-identical points to a timing/state interaction in that critical path, not to a static code defect (all gates passed on the hook). |
| Label update (`setText` during build) | Contributor to the same candidate | The label walk touched live popup views while the popup was being built/shown. |
| `List.set` / `Lwhe.o` substitution | Not independently the cause | The substitution itself is a pure data operation; it becomes a problem only because it happened after the views were bound to the old list. |

**Design consequence:** move the substitution to BEFORE any view is built — substitute the
list at load time, so the popup builder sees the custom list as if it were the original
and never needs any repair. That is exactly what this build does.

## 2. Design — hook the LIST LOAD in `Lqml.c()`, never touch `Lqmu.c()`

`Lqmu.c()` (the popup builder) is **byte-identical to Fix11's** — CanonDiff vs 856/Fix11
classes2 shows `Lqmu.c()` = 0 methods different. The ONLY classes2 change is `Lqml.c()`.

### Why `Lqml.c()` is safe to hook
- `Lqml.c(LinearLayout, SoftKeyboardView, View, F, F, ActionDef, [I)V` is the base popup
  build (33 regs, 602 insns, **0 try blocks**, no switch / no fill-array-data — verified from
  the 856 smali and dex).
- **Insertion point: right after insn 25** — the `IPUT_OBJECT v4, v0, Lqml->e` that stores the
  ActionDef list. The view-inflation loop reads the list from v4 at insns 61 (`Lwhe->size()`)
  and 179 (`Lwhe->get(I)`). BranchDump on 856: **81 branches, ZERO cross insn 25**, so no
  branch straddles the insertion point.
- **v4 survival:** the original code reuses v4 as a temp after insn 25, but the FIRST write
  to v4 after insn 25 is insn 183 — AFTER the list reads at 61/179. So the substituted list
  stored into v4 by the hook survives to both reads. `Lqml->e` is only written in `Lqml.c()`
  (insn 25) and never read there — the hook's second write (new Lwhe into `Lqml->e`) is what
  `Lqmu.c()`'s guard reads.
- **`Lwhe.o` is required:** the loop calls VIRTUAL `Lwhe->size()`/`Lwhe->get()` on v4, so v4
  must hold a `Lwhe`, not a bare ArrayList. The hook re-wraps via the existing static
  `Lwhe.o(Collection)` factory and stores the new Lwhe into BOTH v4 AND `Lqml->e`.
- **No new method refs:** classes2 method_ids is exactly 65536 (full). All 12 method refs
  and 5 field refs the hook needs were already present (Phase 3 used them; method_ids
  stayed 65536). The hook is fully inlined; no helper method.

### What the hook does (296 insns, 550 code units — even)
Inserted right after the list store (`INS=0x30`):
1. **Zero + REF-seed:** `CONST_4` on v5/v8–v15 (dead at entry), then `MOVE_OBJECT` v5/v9/v10/
   v12/v14 from v4 — keeps TypeMergeCheck clean (same discipline as Phase 3).
2. **Fingerprint:** null list → GUARD; `List.size` must be 9; `List.get(3)` → `INSTANCE_OF Lpva`
   → `IGET Lpva->e` (CharSequence) → non-empty → `Character.codePointAt(0)` → v8 = centre
   emoji code point (token[3] is unique across all 26 keys; verified against fd2.xml).
3. **26-way chain** on the centre code point → pref key string `emoji_A`…`emoji_Z` (v12) +
   column class (v13: 0=center, 1=left, 2=right). `GOTO_16` (range-checked in fixup) to PREFS.
4. **Prefs read:** `this.f.b` (`Lqmo->b`, the Context — null-guarded) →
   `getSharedPreferences("nobi_longpress_emoji")` → `getString(key, null)`. Null → GUARD.
5. **`split(",")`** must give exactly 5 parts in canonical order
   `center,up,down,left,right`; otherwise GUARD.
6. **Clone + substitute:** defaults cloned into a new `ArrayList`; 5 new
   `Lpva(codePointAt(custom,0), default item's Lpuz, custom String, g=0x7fffffff)` built
   and `List.set` at the 5 slot indices (same per-column mapping as Phase 3):
   centre `{down 0, centre 3, right 4, left 5, up 6}`; left edge `{1,4,5,3,7}`;
   right edge `{1,4,3,5,7}`. **Each `Lpva->d` read is immediately preceded by
   `INSTANCE_OF … Lpva;` + `IF_EQZ → GUARD`** (the 851 lesson — FieldCheck 0).
7. **Finalize:** `Lwhe.o(ArrayList)` → new Lwhe stored into **v4 AND `Lqml->e`**.
8. **GUARD** (fail-safe): falls through to the original stock code — the list is EXACTLY as
   loaded, zero side effects. Any failure (null list, size≠9, not Lpva, not CharSequence,
   empty, no chain match, null Context/prefs/string, parts≠5) lands here.

**No label update.** The popup builder labels cells from the list; because the list is
substituted BEFORE the build, the labels are already correct. The label walk was only
needed because the Phase 3 hook substituted AFTER the views were bound.

### Registration / register discipline (lessons applied)
- **4-bit register limit (dexlib2, PROVEN):** `CONST_4` (11n), 35c invokes, 22t/22c/12x
  formats only address v0–v15. The first patcher version failed with
  `IllegalArgumentException: Invalid register: v16` — fixed by using only low registers
  (v5, v8–v15) in 4-bit formats.
- **Slot indices computed ON THE FLY, not stored in registers.** The first working patcher
  kept slot indices in v16–v20 (CONST_16) and produced **4 NEW TypeMergeCheck conflicts**
  (I32 vs I64 at the stock double joins 681/815) — because v18/v19/v20 are wide-value
  (double) registers in the stock code, and INTs written into them merge as I32 vs I64.
  The fix: each `setSlot` computes its slot index into v15 from the column id (v13) with a
  short branch sequence (down/centre/up = 4 insns, left = 4 insns, right = 9 insns).
  Result: **TypeMergeCheck 34 = 34, identical profile by location — zero new conflicts.**
  (The stock code itself has 34 pre-existing wide-value-reuse false positives; the hook
  adds none.)
- **v25–v32 (param registers p0–p7) are NOT free** — the original code reuses them as temps
  after insn 25 (proven by smali scan). The hook uses only v5/v8–v15.
- **GUARD is the ONLY fall-through target** for every failure path; the stock tail is
  instruction-identical (verified by TailCompare-style review of the 5 setSlot blocks and
  the finalize in the dump).
- Hook block = 296 insns / 550 units (even); +1 NOP padding included. `Lqml.c` grows
  602 → 898 insns.

### Residual risk (honest)
The SharedPreferences read still happens in the popup-build path (now in `Lqml.c()`,
earlier, before view inflation). After the first call it is a framework-cached in-memory
lookup, so per-call cost is negligible — but the exact micro-mechanism of the Phase 3
failure was never proven from device evidence, so a residual timing risk remains. The
design removes the two strongest candidates (substitute-after-registry-build and the
label repair) and keeps `Lqmu.c()` byte-identical to Fix11, which is the maximum that can
be done statically. **Sam's phone test is the only verdict.**
